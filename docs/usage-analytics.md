# Aggregate usage analytics

Startup counting and improvement reporting have different contracts. Automatic error reports and detailed usage counters require current improvement opt-in. Manual reports continue to require review and explicit Send. Agents cannot enroll a user or approve submission.

On the native application's `ready` event, send one bare `POST https://vibestudio.app/v1/problem-reports/usage/startup`. There is no body, cookie, credential, public key, signature, identifier, version, locale, or client timestamp. It counts all startups, including opted-out and undecided use, so the endpoint does not encode the sharing choice. Do not add a counter notice, setting, or approval prompt to the product UI, as explicitly requested. The existing improvement choice describes the opt-in data only.

The receiving Worker atomically increments one UTC-day aggregate in `usage_daily`, with mode `baseline`, metric `startup`, and a count. It keeps no individual startup row. It rejects bodies, query parameters, authentication/cookie headers, and report identity headers. The connection necessarily has network metadata at Cloudflare; the application uses a transient source-IP digest solely for the rate limiter and never writes it to the database. Worker invocation logs and traces are disabled; the counter handler emits no request logs. This is anonymous aggregate storage, not a promise that an HTTP connection has no network address.

An opted-in runtime batches fixed counters at most once a minute through `POST /v1/problem-reports/usage`, then merges them into the same table under mode `improvement`. The typed schema accepts only startup, reporting-enabled runtime minutes, shell surfaces opened, browser navigation actions, entities/contexts created, and report drafts/previews/queue actions. There are no arbitrary event names or text properties. Navigation URLs, entity arguments, source code, chat, exception messages, account IDs, and machine keys are excluded. Native-owned app/view actions are counted locally; server-owned runtime actions require that server capture owner's own opt-in. Forwarded calls are not counted again by the native runtime. These are selected successful operations, not complete session trajectories or proof of user engagement.

Unknown, stale-policy, and off states cannot send detailed counters. Consent withdrawal clears buffered counters and aborts outstanding detailed requests. Consent is rechecked at flush; consent revisions prevent buffered old choices from being sent after re-enrollment. Counters have no durable outbox, receipt, replay ID, or retry. An ambiguous acknowledgement is never replayed. Offline use, short sessions, transport failures, rate limits, and closing a runtime can therefore produce missing counts. Neither startup nor analytics blocks application use.

The startup guard lives in the native application process, so repeated shell mounting, reconnect, or workspace switching is not another startup. The request is made directly by the trusted application host and does not wait for a workspace, reporting consent, account lookup, or paired server. Runtime minutes measure the lifetime of the reporting runtime that owns that observation while opted in; they do not mean foreground activity or agent working time. Browser-only and mobile startup counting are not added by this change; the baseline is native application launches. Resolving the native reporting owner starts opted-in runtime counters. Server and browser runtimes do not contribute native startup or runtime-minute counts.

`vibestudio-dev` exposes daily totals through developer-authenticated `/admin/analytics?days=N` and unrestricted developer SQL against `usage_daily`. The dashboard shows total startup pings, opted-in counted native startups, the nonnegative difference, and detailed counters. That difference is a rough unseen-startup estimate, including opted-out/undecided use and missing detailed delivery; it is not a count of unique machines or users. Counters cannot join to machine public keys. Report/component/version filters deliberately do not filter these identifier-free totals.

Retain daily aggregates for 400 days. The counter limiter has its own namespace (120 requests/minute per Cloudflare location/source-IP digest). Public counts and client-supplied increments are approximate, rate-limited input, not authenticated population measurements. Developer SQL remains unrestricted. Apply `0002_usage_analytics.sql` when provisioning/upgrading the report database, deploy the new limiter binding, and retain the disabled invocation-log/trace configuration.

The improvement policy is now `problem-reporting.v2`, so an existing older sharing choice cannot silently authorize the added detailed analytics. This reporting system is still pre-release; the current bundle contract uses the current policy only. First use asks for a fresh choice when the policy differs.

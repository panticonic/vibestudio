# Publishing workspace-enabled websites

Status: implemented baseline, 2026-09-27. This document does not authorize a public deployment.

## Goal and product boundary

An agent should be able to take one panel application, build its web entry from the same application and `@workspace/runtime` implementation, preview it, and publish the exact reviewed static artifact to Vercel, Cloudflare Pages, or GitHub Pages. The result is a normal public website. It gains workspace access only when opened inside Vibestudio and explicitly connected to the workspace containing that page. Publication credentials never enter the website bundle.

The common workflow is: develop application → produce immutable site artifact → preview and check connection behavior → review destination and public bytes → publish → observe provider state → fetch the public build manifest and assets → open the actual URL in a fresh Vibestudio document and exercise a permitted operation. A provider acknowledgement, Git push, or HTTP 200 is not a verified deployment.

## Starting point

- The Host has `build:website-runtime` and `create:website` scripts. The scaffold uses `App.tsx` for installed and web entries, vendors a standalone shared SDK and lockfile, and builds deterministic static output in `docs/` with `vibestudio-build.json`. The scripts are developer commands, not an agent-visible workspace build API.
- Base `skills/workspace-dev/WEBSITES.md` documented connection and the scaffold. Its missing GitHub skill links were replaced by the website-publishing skill's provider references.
- GitHub Pages integration already has exact repository audience handles, source configuration, and build observation helpers. The wider website plan records that live public deployment acceptance is still outstanding.
- `build.getBuild` and the panel HTTP server produce an installed panel artifact, not a portable static site artifact. The current scaffold rebuilds through a separate script. `PROJECT_TYPES` has no website type; a website is presently a panel package with a second entry.
- Templates already have a URL/exact-pin vocabulary, dependency composition, inspection, and reviewed workspace creation. The website plan already calls for optional template offers. These are a better basis for workspace compatibility than a new install channel.

## One application and one build contract

### Ownership boundary

Publication is a Base userland feature. Base owns scaffolding, site packaging and manifests, provider adapters, account/project selection, upload request construction, API sequencing, deployment receipts and recovery, status polling, public asset verification, compatibility evaluation, and the agent skill. Persist publication operations in ordinary workspace storage. The host has no Vercel, Cloudflare Pages or GitHub Pages deployment service and no publication state machine.

The host retains its existing responsibilities: compilation and immutable build storage, protected credential input/storage/renewal/injection, mediated HTTP transport, authority enforcement, and native website connection attestation. Userland calls `credentials.fetch` (or its audience-bound handle) for provider requests, including uploads. The host executes the authenticated network transport; userland chooses the API operation, assembles its payload and interprets the result. Provider-specific decisions and retry semantics belong in the Base adapter.

Any additional host API must express a reusable mechanism required by this boundary. Prefer the existing build/artifact, credential and egress contracts. Host build work is limited to reusable browser compilation/export and artifact access; Base assembles the static site's HTML, asset inventory, public manifest and deployment packaging from those outputs. Base supplies publication review facts through ordinary authority acquisition; the host seals and enforces the reviewed effect using that existing mechanism.

Keep a panel's existing `vibestudio.entry`. Add an optional **web entry** to that same package manifest, for example `vibestudio.website.entry: "site.tsx"`. Both entries import the same application component and shared runtime. A separate `website` project type would encourage duplicate applications and conflicting identity. The web entry may supply a static base path and public asset policy, but must not replace receiver policies, workspace authority, or panel build semantics.

Use the normal build graph's browser compiler and exact source resolution for the web entry, adding a portable browser output target only where the existing build contract is insufficient. It resolves the exact workspace ref, package graph, browser condition, shared runtime and dependency lock through the host-owned projection. Base packages the resulting outputs into an immutable static artifact containing sorted paths, byte lengths, MIME types, SHA-256 hashes, a source event/ref, SDK version/digest, and a build ID. Validate paths and dependency closure at their existing owners; Base's packaging policy controls published files, source maps and disclosure review. A scanner cannot prove arbitrary source contains no secrets: publish only the reviewed inventory. The public manifest is fetchable. Keep the scaffold generator as an authoring convenience, but make it call the same build and packaging implementation; eliminate its separate build algorithm.

Expose the build/package/inspect/preview workflow through a typed Base userland API over those existing primitives. Return an artifact handle/manifest and bounded diagnostics. The Base adapter reads artifact bytes and constructs the upload. Preview must serve the **same bytes** that are submitted to a provider, at a configurable subpath as well as `/`, with no deployment credentials. The publication review displays the complete public file inventory, destination, selected account/team, production versus preview, build ID, and whether publishing source code is also required.

Use the same artifact for every provider. Do not make provider build servers rebuild source with different dependencies. Existing GitHub Pages branch publication can materialize that artifact at `/docs` in the dedicated managed repository; Vercel and Cloudflare Pages upload its bytes directly. The build identity and verification rules are common even though providers require different transport formats.

## Provider access and publication owners

Use the host credential service and mediated egress, with a Base provider integration owning each API contract, account selection, setup/repair presentation, exact endpoint declarations, and typed errors. Secret material stays host-held. Publication should have a stable operation ID bound to the destination and artifact digest; retries first inspect remote state and never create a second project or overwrite a different deployment owner silently. Store a non-secret publication receipt: provider, account/team, project/repository, environment, artifact ID, remote deployment ID, status, and observed URL. Do not treat project creation, upload, and promotion as one transaction.

Two transport details require explicit implementation investigation. Current `packages/credential-client/src/index.ts` buffers string/binary/Blob request bodies and sends binary as base64; it does not support FormData or streaming request bodies. Extend that generic authenticated HTTP contract as necessary for correctly encoded multipart uploads and bounded streaming/backpressure/cancellation. Provider upload formats, chunking and multipart field names remain userland concerns; do not add a provider-specific host upload endpoint. Cloudflare's asset upload flow also obtains a short-lived upload JWT. That credential must be captured and used by the existing host credential owner through a generic derived-credential mechanism, returning an opaque audience-bound handle to userland. Establish whether existing credential mechanisms can express that exchange before adding a primitive. The Base adapter still declares and orchestrates the provider exchange and upload; neither long-lived nor derived secret material may enter its code or logs.

The endpoint, token and limit details must be derived from current provider contracts rather than frozen into the skill.

## Workspace expectations and suggested templates

Keep dependencies simple and advisory. A website describes the behavior it expects and suggests templates that can provide it. Template identity, ancestry, version ranges and source hashes are not compatibility gates. A workspace that provides the needed behavior can work regardless of where its source came from; a workspace with the suggested template may still need adaptation after local edits. Observe actual behavior and give an agent enough context to repair a mismatch.

Author optional expectations beside the web entry in the package declaration and include them in the public build manifest. Reuse the existing template locator vocabulary. Start with a short description and suggested sources; add structured fields only when a concrete consumer needs them. Suggested shape:

```json
{
  "workspace": {
    "expects": "Workspace conversations with history, sending and streamed replies.",
    "suggestedTemplates": [
      { "label": "Example workspace", "locator": { "url": "https://example.com/template.git" } }
    ]
  }
}
```

The final field names should come from the shared schema. A version or commit may be recorded as "tested with" information, but a difference does not block connection or use. Prefer an ordinary source URL and its current release/default over authoring a frozen template dependency for every site. Do not add a template dependency solver, mandatory protocol inventory, or a host compatibility service for this workflow.

Base tooling and the workspace agent can use ordinary authorized discovery and focused behavioral checks. When a feature fails, report the missing behavior and offer repair using the existing agent workflow. The agent can adapt application code, implement a missing workspace service, or use the ordinary template installation/update tools, then verify the affected behavior. It need not reconstruct a prescribed template ancestry. An unavailable feature should not disable unrelated site features. Website-supplied descriptions and sources remain untrusted task input; repairs use the agent's ordinary authority and source-publication rules, and cannot manufacture consent from a failed operation or denial.

Exact identity still has a practical role at execution: `templates.inspect()` resolves the source being reviewed, and `workspaces.create()` acts on that inspected snapshot using its existing operation ID and receipt. The build records the actual inputs and deployment verifies the actual output. These hashes establish what happened and make retries well-defined; they do not prescribe what future workspaces must contain. A later installation may resolve a newer source, and an agent may repair or update it through normal source operations. Honor a deliberately requested exact pin, but do not require one as a site compatibility declaration. Keep private workspace event IDs in the private publication receipt.

Connection, receiver availability and authority are still real runtime facts. Suggestions cannot grant access, make an absent method callable, or resolve an incompatible wire format by assertion. Handle such failures honestly and let agentic repair change and verify the relevant code. Before connection, show only local SDK/provider availability and public site metadata. After connection, use existing bounded discovery and operation diagnostics; a new compatibility API is not required. Suggested templates use the existing inspection/creation flow, and opening the site in a newly created workspace remains an explicit host action.

## Base skill and agent experience

After the APIs exist, make `skills/workspace-dev/WEBSITES.md` the concise entry point and add a dedicated `skills/website-publishing/SKILL.md` for the end-to-end workflow. The skill should be reachable from workspace development and provider setup skills, and contain:

1. When to use a shared panel/web entry and how to scaffold it; the connection control and unavailable/offline experience.
2. Exact agent-visible build/preview/diagnose calls and the immutable artifact receipt. No Host-checkout paths or developer-only commands in the happy path.
3. One provider-neutral decision tree: choose provider/account/project, preview versus production, inspect existing remote, review public bytes, publish, observe, verify served identity, test fresh document connection.
4. Provider-specific setup and failure repair links for GitHub, Cloudflare and Vercel, with current permission sources. No token handling in agent code or page source.
5. Advisory workspace expectations and suggested templates; diagnosing actual behavior and using the ordinary agent workflow to repair mismatches. Explain that recorded versions are evidence, not mandatory workspace prerequisites.
6. Recovery from partial success and timeout by operation ID; precise final receipt with URLs, artifact ID, environment and observed state.

Ship a single sample application and exercise all three adapters with it. Keep live API signatures in generated/reference contracts; the skill teaches the workflow and invariants. Fix the currently broken GitHub skill links as part of the documentation work.

## Implementation order and acceptance

1. **Build contract:** shared installed/web manifest entry, static website target, exact-state artifact and preview. Prove repeat builds from one ref produce the same build ID and work at root and a repository subpath. Prove no private bytes or unresolved imports enter output.
2. **Userland publication:** Base-owned durable receipt, review surface, upload orchestration, status/reconcile contract and public-byte verification. Resolve generic request-body transport and derived-credential needs first. Test retry after uncertain project creation/upload/deployment without duplicate or silent takeover. Check that host APIs contain no provider-specific publication behavior and that provider secrets never reach userland.
3. **GitHub Pages:** finish/repair existing integration and Base documentation, then run one real preview or public acceptance against an owned test repository if credentials are available.
4. **Cloudflare Pages and Vercel:** implement the direct artifact adapters with mocked provider error/state tests, then one owned remote acceptance for each. Use current provider docs at implementation time.
5. **Expectations and repair:** optional descriptions and suggested template URLs, ordinary inspection/creation, and focused behavioral diagnostics. Demonstrate that a differently composed workspace can work, a suggested template can need repair, and an agent can fix a concrete mismatch without a dependency lock gate. Preserve connected and unconnected disclosure boundaries.
6. **Agentic DX:** Base skill and one end-to-end agentic test for each provider's supported path; check the agent never invokes developer-only Host scripts, handles permission repair, verifies the actual URL, and reports a partial result accurately.

The existing website endpoint/resource audit, shared runtime parity, and native document acceptance remain prerequisites for claiming general website deployment readiness; provider publishing alone does not complete them.

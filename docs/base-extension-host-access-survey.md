# Base extension host-access survey

> Isolation planning (2026-09-05): [Cross-platform isolation](isolation-plan.md) is canonical for isolation architecture, implementation order and acceptance gates. The survey remains evidence; its proposed follow-up is superseded by U0–U6.

> Subsequent approved scope: commands and native extensions share a workspace sandbox; cancellation is best effort. The recommendations below for per-job/context isolation, private native-client secrets and guaranteed descendant retirement are historical, superseded by the canonical plan. The extension inventory and host-access findings remain applicable.

Date: 2026-09-05. Static source review; no isolation implementation or runtime containment tests were performed.

The Base extensions do not require a generally privileged extension runtime. All 13 can remain inside an app boundary, provided a few operations are mediated by installed native code and hardware access is explicitly scoped. Native Node APIs, subprocesses, PTYs, and disk-backed workspace projections are requirements of the execution environment; they do not imply access to the user's surrounding machine.

The architectural recommendation is an isolated app execution domain plus a small native broker. Do not classify entire workspace extensions as trusted host plugins. The boundary must cover the hub/server, extension processes, workerd, build tools, test processes, terminal children, and local inference children, as well as the desktop app. Leaving the server or Electron main generally privileged would leave substantial app code outside the intended boundary.

App-owned storage may physically reside on the host while still being explicitly included in the sandbox.

## Important details behind the exceptions

### Browser import: preserve the existing separation

[browser-data/index.ts](/home/werg/vibestudio-release-work/base/extensions/browser-data/index.ts:270) delegates native access. [BrowserImportHostProvider](/home/werg/vibestudio/src/main/services/browserImportHostProvider.ts:110) already retains raw source paths locally and exposes opaque sources and bounded frames. Sensitive cookie/password/form-fill batches go directly to the browser vault rather than the workspace extension. This is a useful contract to preserve when introducing an OS boundary.

The native importer searches browser profile roots, including native, Flatpak and Snap installations ([paths.ts](/home/werg/vibestudio/packages/browser-import/src/detection/paths.ts:1)). Its platform implementations use Linux Secret Service/KWallet tools, macOS Keychain through `security`, and Windows DPAPI through PowerShell ([Linux](/home/werg/vibestudio/packages/browser-import/src/crypto/platforms/linux.ts:1), [macOS](/home/werg/vibestudio/packages/browser-import/src/crypto/platforms/darwin.ts:1), [Windows](/home/werg/vibestudio/packages/browser-import/src/crypto/platforms/win32.ts:1)). These privileges belong to the acquisition operation, not to every extension.

The grant should identify the selected browser source, requested categories and operation lifetime. Profile discovery itself reveals installed browsers and profile metadata, so it also belongs behind that grant model. Where practical, acquire a consistent bounded snapshot and parse it in a restricted helper. Do not give the whole app the session bus, the entire Keychain, or all browser directories. Browser exports offer an additional acquisition option where native decryption is unavailable. Current Chromium v20 decryption is explicitly unsupported ([chromiumCrypto.ts](/home/werg/vibestudio/packages/browser-import/src/crypto/chromiumCrypto.ts:145)); more filesystem permission will not implement that missing support.

The vault can remain in an app-owned protected compartment; it need not be an unconfined host service. Keep its decryption and use authority separate from arbitrary workspace code if the existing sensitive-data separation is to be meaningful against a compromised extension.

### Mobile development: distinguish a device operation from running a build

[mobile-debug/index.ts](/home/werg/vibestudio-release-work/base/extensions/mobile-debug/index.ts:11) is only an RPC facade. [mobileNativeService.ts](/home/werg/vibestudio/src/server/services/mobileNativeService.ts:58) contains the native effects. Several build/install operations require a complete Vibestudio source checkout, making them developer integrations rather than prerequisites for an ordinary installed app.

Broker operations should bind to a selected device/simulator and, where applicable, application identity and exact forwarded ports. Passing through an entire adb socket permits much broader device control. The existing `shell` operation is broad Android-device authority, not host-shell authority; that distinction should remain visible in the grant.

A fixed RPC method name does not make a native build safe outside confinement. Gradle/Xcode builds can execute build scripts. Keep those executions restricted to their build inputs, outputs, SDK and necessary signing operation. Do not let a native broker execute arbitrary workspace scripts with its own privileges. Metro bundling in [react-native/index.ts](/home/werg/vibestudio-release-work/base/extensions/react-native/index.ts:128) can stay entirely inside independently of device integration.

### Local models: hardware and storage are separate capabilities

[hardware.ts](/home/werg/vibestudio-release-work/base/extensions/local-models/hardware.ts:132) probes `nvidia-smi`, `rocm-smi`, `vulkaninfo`, `/proc/cpuinfo` and macOS CPU information. GPU device/driver exposure must match the selected backend; it is not a justification for exposing all of `/dev` or host process information. CPU and memory observations should reflect usable sandbox limits when limits are applied.

The default `~/.vibestudio/local-models` directory is an app-owned hardware-asset cache, not a requirement for the real host home ([index.ts](/home/werg/vibestudio-release-work/base/extensions/local-models/index.ts:202)). Preserve intentional sharing across workspaces as an explicitly owned app cache if desired.

`importDir()` records absolute paths with `importedInPlace: true`; it does not copy the GGUF files ([library.ts](/home/werg/vibestudio-release-work/base/extensions/local-models/library.ts:673)). Therefore retaining that feature requires a durable read grant to selected model files/directories, or a deliberate change to copy them into managed storage. Merely returning a host path from a picker will not make it usable across the boundary. Private inference listeners should remain on the app's internal network and not require access to unrelated host loopback services.

### Claude and shells: ambient host state is a dependency to remove or acquire explicitly

[shell/index.ts](/home/werg/vibestudio-release-work/base/extensions/shell/index.ts:31) retains `HOME` and `PATH`; shell startup files can introduce further host dependencies. A controlled app toolchain and private home eliminate that ambient relationship. Shell executability, PTYs and native tools remain available inside the container.

The shared Claude materializer copies `CLAUDE_CONFIG_DIR/.credentials.json` or `~/.claude/.credentials.json` into an isolated profile, and reconciliation may update the original file ([materialization](/home/werg/vibestudio/packages/shared/src/claudeLaunchProfile.ts:224), [reconciliation](/home/werg/vibestudio/packages/shared/src/claudeLaunchProfile.ts:334)). If host-login reuse is retained, both acquisition and refresh writeback need explicit authority. Scope any writeback to the selected credential resource with concurrent-change protection; do not export a generic host file-write operation. The materializer's file-based behavior should not be assumed to cover every platform's credential backend.

The existing [confineClaudeReadOnly](/home/werg/vibestudio/packages/shared/src/claudeReadOnlyLaunch.ts:145) is Linux-only and mounts `/` read-only, binds host `/dev`, and does not unshare the network or PID namespace. Its purpose is protecting managed source writes. It does not establish host confidentiality. Nested under a real outer boundary, `/` would refer to that already restricted filesystem, but nested sandbox startup still needs verification. The top-level launcher cannot use the present declaration as its isolation policy.

### Local source development is an explicit integration

The configured Base adds `readDevelopmentTemplateSources()` and copies a selected checkout during template acquisition ([source.ts](/home/werg/vibestudio-release-work/base/extensions/template-composer/source.ts:202)); this code is absent from the shipped Base pin. Preserve exact snapshots as inputs, with only selected source directories accessible to the acquisition component.

The host's source-session workflow also projects workspace publications back into the configured Base checkout ([README](/home/werg/vibestudio/README.md:192)). Supporting that workflow requires a selected-checkout publication grant outside the app boundary. Build/test execution and the disposable development instances still belong inside. Source publication and installing a new executable host release are separate effects; neither should confer ambient host execution authority.

## Boundary design

1. **Start the complete execution domain confined.** Use an app-owned writable profile, state, cache, workspace projections and private temporary storage. Supply runtime/toolchain files read-only. Detached subprocesses and native dependency children stay in that domain. The trusted launcher/broker is installed code whose executable and configuration cannot be rewritten from it.
2. **Expose resources by operation.** Browser acquisition, device operations, selected-file import/export, credential use and native desktop actions are the broker's vocabulary. Avoid generic `host.exec`, `host.readFile(path)` or `host.connect(host, port)` holes. Reuse existing RPC concepts, but move enforcement to the actual OS boundary.
3. **Make grants concrete and revocable.** Bind them to the authenticated isolated domain, selected resource, operation, read/write direction and lifetime. Have trusted UI or OS selection establish authority. The broker must not accept an untrusted caller's assertion that a manifest or in-app approval granted host access. Prefer handles/opaque IDs to re-resolved paths; close handles and revoke routes on release.
4. **Default-deny ambient inheritance.** The [extension launcher](/home/werg/vibestudio/packages/extension-host/src/processManager.ts:75) currently spreads `process.env` and uses ordinary Node children ([process adapter](/home/werg/vibestudio/packages/process-adapter/src/index.ts:77)). Filter environment and inherited handles at domain creation. Neither extension manifests nor ordinary child-process separation constrain raw Node filesystem/network APIs.
5. **Treat network isolation as part of host isolation.** Public web browsing may need broad Internet access; that is different from access to host loopback, LAN, link-local services, or local control sockets. Enforce the chosen destination policy outside untrusted code. `HTTP_PROXY` by itself is advisory for arbitrary native processes. The current workerd path already routes outbound through an egress service; preserve that instead of relying on historical audit claims that it was unwired.
6. **State the scope of the guarantee.** One shared outer container protects the surrounding machine. It does not isolate extensions from each other's app data, RPC tokens or browser secrets. Shared readable tokens cannot identify distinct hostile processes reliably. Existing within-app authority boundaries need OS-backed separation where those assets must remain protected from native extension code. Full graphics/device grants also expose kernel/driver attack surface; lightweight isolation is not a separate-kernel guarantee.

## Platform assessment

These are implementation directions requiring real platform validation, not claims that the current app already runs under them.

- **Linux:** bubblewrap is a good match. Construct an initially empty filesystem with explicit mounts, private PID/IPC/network namespaces, private home/temp, minimal devices, an appropriate syscall policy and controlled network forwarding. Preserve Electron's own renderer sandbox. Bubblewrap supplies mechanisms rather than a security policy, and warns that broad D-Bus access and incompatible nested sandbox restrictions can undermine the result. [Bubblewrap documentation](https://github.com/containers/bubblewrap).
- **Linux desktop connections:** use portals and restricted IPC where practical. Sharing the host network namespace also exposes abstract Unix sockets; granting broad session-bus or X11 access is not a narrow integration. Prefer a restricted display arrangement and explicit per-service routes, and document any X11 fallback's weaker boundary. [Flatpak sandbox permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html).
- **macOS:** evaluate signed App Sandbox targets and small XPC services, with selected-file grants/security-scoped bookmarks and explicit entitlements. Apple documents child sandbox inheritance and recommends XPC for privilege separation. Broad outgoing-network entitlement is not a per-destination network policy. [Apple entitlement reference](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html).
- **macOS packaging is a real design constraint:** Electron documents that only its MAS build supports App Sandbox; the standard `darwin` build fails under it. MAS builds also have feature differences. Test the actual Electron/Node/workerd/PTY/native-module/downloaded-engine stack with its intended signing and distribution route before committing to this backend. A generic “Mac equivalent of bwrap” wrapper is not established by this survey. [Electron App Sandbox guide](https://www.electronjs.org/docs/latest/tutorial/mac-app-store-submission-guide).
- **Windows:** investigate AppContainer, or LPAC where compatible, with capability SIDs, explicit file/IPC ACLs and a native broker. Use Job Objects for process-tree lifetime/resource management in addition to access controls. Validate Electron, node-pty/ConPTY, workerd, GPU drivers, native module loading and local IPC; a process-group abstraction alone does not provide the proposed boundary. [AppContainer implementation](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer), [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

Electron's ordinary renderer sandbox does not by itself confine the Node server and main process; it is an additional internal protection. [Electron process sandboxing](https://www.electronjs.org/docs/latest/tutorial/sandbox).

## Suggested next proof

Build one Linux containment prototype covering the full app domain, with browser/device broker calls as the only native integrations initially exercised. Confirm normal shell, ripgrep, image/PDF, native tests, typecheck/npm, Metro, Git/template and worker operation. Verify that a malicious extension and its grandchildren cannot read a host-only canary, write outside grants, reach a host loopback service, access host control sockets or continue after the domain is retired.

Then verify each intended crossing: selected browser/category import with sensitive data routed to the vault; selected model files and GPU; selected-device operations; credential refresh; file export; preview/OAuth/remote network routes. Test wrong-resource requests and grant revocation, not just successful calls. Run early macOS and Windows compatibility prototypes before expanding policy abstractions. Failure to support an essential native runtime under a backend is architectural evidence to resolve, not a reason to launch it unconfined.

No test instances were started during this survey. The conclusions establish which authority is necessary and where to place it; empirical compatibility and adversarial enforcement remain implementation work.
